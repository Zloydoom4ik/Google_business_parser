# Google_business_parser

Выгружает фотографии точек Google Maps: метаданные в Postgres, файлы владельца на диск.

Работает через внутренние запросы публичных Карт (те, которыми страница точки подгружает карточку и галерею),
не через официальный Business Profile API. Обычные HTTP-запросы из Python: браузер и вход в Google не нужны.

## Установка (один раз)

Нужен Docker.

```
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
copy .env.example .env
copy places_example.json places.json
```

После этого в `places.json` вписываются настоящие точки — см. раздел «Список точек».

## Запуск

```
docker compose up -d --wait
.venv\Scripts\activate
python main.py sync
python main.py sync_posts
python main.py status
```

## Команды

| Команда | Что делает |
|---|---|
| `python main.py sync` | Фото галереи. По каждой точке из `places.json`: сверяет название и адрес, забирает список галереи, пишет его в таблицу `photos`, качает новые фото владельца в `data\<точка>\photos\` |
| `python main.py sync_posts` | Посты. Те же точки и та же сверка; пишет посты в таблицу `posts`, качает их картинки в `data\<точка>\posts\` |
| `python main.py status` | Сводка по базе. В Google не ходит и ничего не меняет |

Порядок работы `sync` и `sync_posts`: точка за точкой; по каждой сначала данные в базу, потом её файлы.

Карты отдают только 10 последних постов точки. Пост, выпавший из этой десятки, из базы не удаляется.

Пример вывода `status` для одной точки:

```
Fusion Repair - 20 W 30th St
  Google claims 127, listed 100; rows in the database 100; synced 2026-10-06 19:27
  owner photos 95 (files on disk 95, 311 MB), customer photos 3, videos 1, panoramas 1
  posts 10 (picture files on disk 10); synced 2026-10-06 19:12
```

- первая строка — сколько объектов галереи заявил Google, сколько отдал списком, сколько строк точки в `photos`, время последнего `sync`;
- вторая — фото владельца и сколько из них скачано, фото клиентов, видео, панорамы;
- третья — посты, сколько их картинок скачано, время последнего `sync_posts`.

## Список точек: `places.json`

В этот файл вписываются точки, которые надо выгружать. Сам файл в git не попадает;
`places_example.json` — образец с выдуманными данными.

Достаточно одной ссылки на точку:

```json
[
  {
    "maps_url": "https://www.google.com/maps/place/Example+Repair+Shop/data=!4m6!3m5!1s0x0000000000000001:0x0000000000000001!8m2!3d40.7000000!4d-74.0000000!16s%2Fg%2F11aaaaaaaa"
  },
  {
    "name": "Example Repair Shop",
    "address": "45 Second Ave",
    "maps_url": "https://www.google.com/maps/place/Example+Repair+Shop/data=!4m6!3m5!1s0x0000000000000002:0x0000000000000002!8m2!3d40.7100000!4d-73.9900000!16s%2Fg%2F11bbbbbbbb"
  }
]
```

Как получить ссылку: открыть точку на Google Maps так, чтобы слева была её карточка, и скопировать адрес из адресной строки целиком.
Обрезать ничего не нужно — лишние части ссылки программа пропускает.

Поля одной точки:

- `maps_url` — обязательно. Ссылка на точку из адресной строки браузера (не короткая `maps.app.goo.gl`): в ней должен быть номер точки вида `!1s0x…:0x…`.
- `name` и `address` — необязательно. Если их нет, программа берёт название и адрес у Google сама;
  когда у точки на Картах нет адреса (выездная компания), записывается `no_address`, когда нет названия — `no_name`.
- Если `name` или `address` указаны, они сверяются с Google, и при расхождении точка пропускается. Это защита от перепутанной ссылки:
  `name` — буква в букву, как на Картах; `address` — адрес до первой запятой, как его показывают Карты на английском.

Папка точки в `data\` называется `<название> - <адрес>` и закрепляется при первой выгрузке: если название или адрес на Google потом изменятся, папка останется прежней.

Одна и та же точка дважды в файле не нужна: точка определяется номером `!1s0x…:0x…` в ссылке, а не названием.

## Как `sync` сверяет базу с Google

`sync` ничего не очищает и заново не качает. По каждой точке он берёт у Google список галереи и сравнивает его с базой по номеру фото:

| В списке Google | В базе | Что делает программа |
|---|---|---|
| Есть | Нет | Добавляет строку; если это фото владельца — качает файл |
| Есть | Есть | Обновляет данные в строке, файл не трогает |
| Нет | Есть | Удаляет строку из базы и файл с диска |

- Файл качается только тогда, когда в строке ещё не записан путь к нему. Если закачка оборвалась, следующий запуск докачает недостающее.
- Третья строка означает: фото, удалённое из профиля Google, после следующего `sync` пропадает и у нас — без записи о том, что оно было.
  Пустой ответ Google за «всё удалили» не считается, в этом случае ничего не удаляется.
- В базу попадает всё, что Google отдал списком: фото и видео с пометкой `owner` / `customer` и панорамы Street View (`google`).
  Файлы качаются только для фото владельца.

У `sync_posts` первые две строки таблицы работают так же, а удаления нет: посты из базы не удаляются никогда.

## Потоки

Файлы качаются в 8 потоков: одновременно в работе до 8 файлов одной точки. Число задаётся константой `WORKERS` в `gbp_parser/download.py`.
На замере 95 файлов (311 МБ) скачались примерно за 22 секунды вместо 106 при закачке по одному.

Параллельно идёт только скачивание файлов. Запросы данных к Картам и запись в базу — по одному, точки обрабатываются друг за другом.
Строки `downloaded …` печатаются по мере готовности файлов, а не по порядку списка.

## Что где

| Файл | Что делает |
|---|---|
| `places.json` | Список точек: ссылка на Картах, по желанию название и адрес для сверки |
| `gbp_parser/maps_client.py` | Запросы к Картам: карточка точки, список фото, список постов |
| `gbp_parser/parse.py` | Разбор ответа: id, дата, кто загрузил, размер, ссылка |
| `gbp_parser/db.py`, `schema.sql` | Таблицы `places`, `photos` и `posts` |
| `gbp_parser/download.py` | Скачивание оригиналов в `data/<точка>/photos/` и `data/<точка>/posts/` |
| `gbp_parser/places.py` | Чтение `places.json` и сверка названия и адреса точки |
| `gbp_parser/posts.py` | Посты: разбор ответа и команда `sync_posts` |
| `gbp_parser/__main__.py` | Команды `sync`, `sync_posts` и `status` |

## Сколько объектов выгружается: `PAGE_SIZE`

У одной и той же точки Google называет три разных количества. Пример — Fusion Repair, 20 W 30th St (`places.id = 3`):

| Что | Сколько | Где это видно |
|---|---|---|
| Счётчик Google | 127 | `places.google_claims`. Просто цифра из ответа Google, от настроек не зависит |
| Отдаётся порциями по 100 | 114 | — |
| Отдаётся порциями по 20 — столько видит человек на Картах | 100 | `places.google_listed` и число строк точки в `photos` |

- **100** — это 98 фото (95 владельца + 3 клиентских), 1 видео и 1 панорама. Файлов на диске 95.
- **Ещё 14** (до 114) — фото владельца, которые Google отдаёт только при больших порциях. На сайте Карт их не видно.
- **Ещё 13** (до 127) — не отдаются ни при каких настройках. По ним нет ни данных, ни файлов, известна только сама цифра счётчика.

Размер порции задаётся в `gbp_parser/maps_client.py`, константа `PAGE_SIZE`:

| `PAGE_SIZE` | Что выгружается |
|---|---|
| `20` (сейчас) | То же, что видит посетитель Карт: сайт сам просит по 20 |
| `100` | Всё, что Google готов отдать, включая фото, скрытые с сайта. Значения больше 100 ничего не добавляют |

После смены значения нужно запустить `python main.py sync`. При переходе с 20 на 100 недостающие фото докачаются;
при переходе обратно на 20 они удалятся из базы и с диска (правило «нет в списке — удаляем»).

Google нигде не помечает дубликаты. Точные копии находятся по совпадению `photos.file_sha256` — отпечатка скачанного файла.

## Запросы к Google и его ответы

Всё ниже — настоящие запросы и ответы при выгрузке фото точки Fusion Repair, 20 W 30th St (`places.id = 3`).
Длинные служебные куски заменены на `…`. Запросы A и B делаются один раз за запуск, C–E — на каждую точку, F — на каждый новый файл.

### A. Начать сессию

```
GET https://www.google.com/maps?hl=en
```

Ответ: `200`, HTML. Google перенаправляет на страницу согласия с куки:
`https://consent.google.com/m?continue=https://www.google.com/maps?hl=en&gl=NL&…`

### B. Ответить «Отклонить все» на форму согласия

```
POST https://consent.google.com/save
gl=NL  hl=en  continue=https://www.google.com/maps?hl=en  set_eom=true
+ служебные поля со страницы согласия: bl, escs, x, m, app, pc, src, uxe, cm
```

Ответ: `200`, возврат на `https://www.google.com/maps?hl=en`. В сессии появляются куки
`SOCS`, `__Secure-ENID`, `__Secure-BUCKET`, `SEARCH_SAMESITE`.
Без этого шага запрос E возвращает вместо галереи одну панораму.

### C. Страница точки

```

```

Ответ: `200`, HTML около 207 КБ. Из него берётся только одна ссылка — адрес карточки точки:
`/maps/preview/place?authuser=0&hl=en&gl=nl&q=Fusion+Repair&pb=!1m21!1s0x89c25929d8effddf:0x36ef76158161a142!2sFusion+Repair!…`

### D. Карточка точки

```
GET https://www.google.com/maps/preview/place?authuser=0&hl=en&gl=nl&q=Fusion+Repair&pb=…
```

Ответ: `200`, JSON около 108 КБ, первой строкой идёт защитная приставка `)]}'`. Используются два значения:

### F. Файл фото

```

```

Ссылка та же, что в ответе E, только хвост `=w203-h135-k-no` заменён на `=s0` — «исходный размер».
Ответ: `200`, `image/jpeg`, 3 625 351 байт — сам файл 6045×4030. Запрос делается только для фото владельца, у которых файла ещё нет.

Команда `python show_request.py` сохраняет настоящий запрос E и ответ на него в папку `request_example\`.
